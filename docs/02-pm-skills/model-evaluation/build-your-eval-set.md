# 从零建设评测集:用例从哪来、标准答案怎么定

## 为什么"没有评测集就没有迭代"

AI 产品经理最容易踩的一个坑,是把"效果好不好"这件事完全交给算法同学的直觉:跑几个例子看着顺眼,就上线了。这套打法在传统产品里问题不大,但在 AI 产品里会直接反噬——大模型的输出是概率性的,同一个 Prompt 换一批输入,效果可能天差地别;没有一套稳定、可复现的测试集,你永远不知道"这次改动到底是变好了还是变差了",也无法在两个模型、两版 Prompt 之间做客观对比。

Anthropic 官方把这件事说得很直接:构建评测(evals)和定义成功标准,是 Prompt 工程与模型迭代的核心闭环——先有标准,再有测试集,再有迭代;反过来,没有测试集,连"标准"是否达成都无从验证。这也是为什么"评测体系"几乎是所有大厂 AI PM 面经里的高频题(参见 [如何构建大模型效果评测体系?](../../04-interview/basics/model-evaluation-system.md))。本篇聚焦"评测集"这一个具体环节:用例从哪里来、覆盖度怎么设计、标准答案怎么定、规模要多大、以及如何管理它的生命周期。

## 用例的四个来源

一个健康的评测集,不应该只来自某一个渠道。常见的四类来源各有侧重,实践中通常要组合使用:

| 来源 | 说明 | 优点 | 局限 |
|------|------|------|------|
| 真实用户日志 | 从生产环境采样真实提问/对话 | 最贴近真实分布,覆盖长尾表达 | 可能缺少标准答案,需要人工标注;敏感信息需脱敏 |
| 专家构造 | 产品/业务专家根据场景设计用例 | 覆盖度可控,能补全日志里没出现过的重要场景 | 容易带专家的思维定式,可能脱离真实用户语言习惯 |
| Badcase 回流 | 把线上发现的错误案例沉淀进评测集 | 直接对应真实问题,修复后能验证是否真的解决 | 需要配合归因流程(见[《Badcase 分析方法论》](badcase-analysis.md)),否则容易只是"头痛医头" |
| 对抗样本 | 刻意构造的边界、模糊、恶意输入 | 暴露模型的脆弱点和安全风险 | 需要专门设计,产出效率低于前三类 |

OpenAI 的评测最佳实践建议把"生产数据 + 专家标注数据 + 合成数据"混合使用,并可以用模型本身来辅助生成多样化的测试样本——比如给模型看一批已有用例,让它模仿风格再生成更多变体,缩短人工编写的时间。Anthropic 的文档也提到同样的技巧:"手写几百条测试用例很费时间,可以让 Claude 从一小批示例中扩展生成更多"。这提示我们,评测集建设不必事事纯手工,人工负责定义标准和把关质量,模型负责放量。

## 覆盖度设计:典型、边界、攻击

只覆盖"正常路径"的评测集会严重高估真实效果,因为线上流量里总有一部分是模型没见过的怪异输入。Anthropic 官方建议评测设计要"镜像真实世界的任务分布",并特别列出几类必须覆盖的边界场景:

- **无关或缺失的输入数据**(比如空输入、答非所问的追问)
- **超长输入**(远超正常长度的用户输入或上下文)
- **[对话场景] 恶意、有害或无关的用户输入**
- **模糊案例**——连人类专家都难以达成一致判断的场景

OpenAI 的分类方式类似,把边界情况归纳为三类挑战:

| 挑战类型 | 具体表现 |
|----------|----------|
| 输入多样性 | 多语言、不同格式(表格/代码/图片)、多模态混合输入 |
| 上下文复杂性 | 一句话里夹带多重意图、超长多轮对话、指代/数据歧义 |
| 个性化与冲突 | 用户尝试越狱、用户指令与系统 Prompt 冲突 |

实践中一个简单可执行的配比原则是:**70% 典型场景(保证基本盘不崩)+ 20% 边界场景(暴露薄弱环节)+ 10% 攻击/对抗场景(守住安全底线)**。具体比例要按业务风险调整——医疗、金融等强合规场景,对抗样本占比应显著提高。

## 标准答案与评分标准:客观题 vs 主观题

评测集里每一条用例都需要"怎么判断对错"的依据,但不同任务类型的判断方式差异很大。Anthropic 官方把评分方法按"速度、可靠性、可扩展性"排了优先级:

1. **代码评分(Code-based grading)**:最快最可靠,扩展性最强,但缺乏处理复杂判断的灵活性。适合有唯一正确答案的客观题。
   - 精确匹配:`output == golden_answer`
   - 字符串匹配:`key_phrase in output`
2. **人工评分(Human grading)**:最灵活、质量最高,但慢且贵,应尽量避免作为常态方案,更适合校准和抽检。
3. **LLM 评分(LLM-based grading)**:速度快、灵活、可扩展,适合复杂主观判断,但需要先验证可靠性再放量使用(详见[《主观任务怎么评》](llm-as-a-judge.md))。

### 客观题:一个答案就是一个答案

分类、抽取、格式合规类任务适合客观评分,标准答案通常是唯一确定的:

```text
用例:判断这条微博的情感倾向
输入:"这电影简直浪费我两小时。👎"
标准答案:negative
评分方式:exact match(去除大小写、首尾空格后完全匹配)
```

### 主观题:标准答案是一份 rubric,而不是一句话

生成式任务(总结、客服回复、创意文案)往往没有唯一正确答案,这时"标准答案"应该是一份可执行的评分标准(rubric),而不是一段参考文本。一个可用的 rubric 示例:

```text
【客服回复质量评分 rubric】满分 5 分

1. 是否准确引用了工单中的关键信息(订单号/问题描述)?(2分)
   - 完全准确 = 2分;部分准确 = 1分;缺失或错误 = 0分
2. 语气是否符合"耐心、专业、不推诿"的要求?(2分)
   - 完全符合 = 2分;基本符合但生硬 = 1分;冷淡或推诿 = 0分
3. 是否给出了可执行的下一步(而非空泛安慰)?(1分)
   - 有明确下一步 = 1分;没有 = 0分

低于 3 分判定为不合格,需要人工复核。
```

Anthropic 对 LLM 评分 rubric 的建议是:**尽量具体、可量化**,例如"回答的第一句必须提到公司名称,否则自动判为不合格",而不是"回答要专业得体"这种无法量化的描述;同时建议**让模型先给出推理过程再输出结论,再丢弃推理只保留结论**,这样能显著提升复杂判断任务的评分准确性。

## 规模多大才够

一个常见误区是认为"评测集越大越好"或者反过来"几个例子就够了"。官方给出的经验法则更实用:

- Anthropic 建议:**优先追求数量而非单条质量**——"更多的题目、用自动化评分(即便信号略弱),好过少量题目但纯靠人工精评"。
- 对于 Agent/复杂任务场景,Anthropic 工程博客给出了更具体的起步建议:**20-50 个来自真实失败案例的简单任务,就是一个很好的起点**,不需要等到"完美的评测套件"才开始。
- 覆盖度比绝对数字更重要:如果任务场景单一(比如固定格式的分类任务),小几十条就可能收敛;如果场景复杂多变(比如开放域客服对话),几百到上千条才能反映真实分布。

一个可参考的启动节奏:先用 20-50 条真实 badcase 搭起最小可用评测集 → 跑通评分流程 → 再逐步扩充典型/边界/对抗样本到覆盖目标场景的规模。

## 评测集也要版本管理

评测集不是一次性交付物,而是需要长期维护的"活的资产"。几个关键实践:

- **像代码一样管理版本**:每次新增/修改用例都要记录变更原因和时间,否则无法解释"为什么这次分数波动了"。
- **明确责任人**:建立专门的所有权(ownership),否则评测集会随着产品迭代逐渐过时、无人维护。
- **开放贡献通道**:让产品经理、客服、运营都能提交新发现的 badcase 进入评测集,而不是只靠算法同学维护。
- **警惕"评测饱和"**:当某个能力项的评测分数长期稳定在 100% 时,说明这批用例已经不再有区分度,应该把它降级为"回归测试集"(防止旧问题复发),同时开辟新的、更难的用例来衡量当前的能力边界。

## 上线验收流程怎么设计

评测集建好之后,最终要服务于一个具体决策:**这个模型/这版 Prompt,能不能上线?** 一套可落地的验收流程通常包含以下步骤:

| 步骤 | 内容 | 产出 |
|------|------|------|
| 1. 定义验收标准 | 上线前对齐:哪些指标必须达标(如准确率 ≥ 90%)、哪些是一票否决项(如安全红线、隐私泄露) | 验收标准文档,产品/算法/业务三方签字确认 |
| 2. 离线评测 | 在评测集上跑分,产出分维度报告 | 评测报告(含通过率、典型失败案例) |
| 3. 差异复核 | 对比上一版本,人工抽查显著变化的用例,确认是真提升还是评测集漂移 | 复核记录 |
| 4. 灰度验证 | 小流量上线,观察真实业务指标(不只是模型分数) | 灰度报告 |
| 5. 正式上线签署 | 产品、算法、业务三方确认验收标准达成,留痕存档 | 上线审批记录 |
| 6. 上线后追踪 | 上线后 1-2 周内密切监控 badcase 增量和业务指标 | 复盘报告,新增 badcase 回流评测集 |

这里最容易被忽视的一环是"一票否决项"——准确率再高,只要触碰安全/合规红线就不能上线,这条线必须在评测设计阶段就写清楚,而不是等出了问题再补救。
