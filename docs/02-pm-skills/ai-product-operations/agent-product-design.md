# Agent 产品生产化：从会执行到可负责地完成任务

Agent 产品不是“给大模型接几个工具”就结束了。生产化的核心，是把模型的自主决策放进一份明确的产品契约：它要完成什么任务、可以调用什么、什么时候必须停下来问人、失败后怎么退回、花费到哪里必须刹车，以及什么证据足以证明任务真的完成。

> **事实**：Anthropic 将固定路径编排的系统称为 Workflow，将由模型动态决定步骤和工具使用的系统称为 Agent；OpenAI 的 Agent 指南也把模型、工具、指令与防护机制视为一个需要整体设计的系统。Agent 因为路径不完全固定而更灵活，也因此更难预测。见文末官方资料。
>
> **建议**：AI PM 不要先问“要不要做 Agent”，而要先问“这项任务是否多步骤、是否需要外部动作、每一步能否验证、出错代价是否可接受”。

## 一、先定义任务，不先定义 Agent

一个可生产化的 Agent，首先应该有一张**任务卡(Task Contract)**。任务卡不是技术方案，而是产品、算法、工程、安全和运营共同认可的边界。

| 字段 | 要回答的问题 | 可验收的写法 |
|------|--------------|--------------|
| 用户目标 | 用户到底想完成什么，而不是想让模型说什么？ | “把本周待处理工单按优先级分组，并生成待确认清单” |
| 触发条件 | 什么输入会启动任务？什么输入直接拒绝？ | 规定输入来源、格式、数据范围和不支持场景 |
| 任务范围 | Agent 能做哪些子任务，不能碰哪些系统或数据？ | 明确允许的工具、资源、租户和操作类型 |
| 完成标准 | 什么证据说明任务完成？ | 结果字段齐全、关键工具返回成功、业务规则校验通过 |
| 人工介入 | 哪些节点必须由人确认或接管？ | 金额、删除、外发、权限变更等副作用动作先确认 |
| 失败出口 | 失败后是重试、降级、暂停还是转人工？ | 每类错误对应唯一的下一步和用户提示 |
| 预算边界 | 一项任务最多消耗多少调用、时间和费用？ | 到达任一上限就停止自主循环并说明原因 |

**完成标准不等于模型说“完成了”。**模型输出的自然语言只能是一个候选结果；真正的完成状态应由工具结果、业务校验、人工确认或用户验收共同决定。比如“已发邮件”至少需要邮件服务返回可追踪的发送结果，而不是 Agent 生成一段“邮件已发送”的文字。

## 二、任务拆解：选择 Agent、Workflow 还是混合方案

先把任务画成路径，再决定哪里让模型自主规划：

```text
用户目标
  ↓
输入校验 → 固定步骤？ ── 是 ──→ Workflow/规则流程
  │                         │
  否                        └─ 关键节点仍可调用模型
  ↓
允许的计划范围 → 工具调用 → 结果校验 → 继续/重试/人工确认/结束
```

| 场景特征 | 推荐形态 | PM 的重点 |
|----------|----------|-----------|
| 步骤固定、规则清晰、错误代价高 | Workflow 或规则流程 | 把分支、权限和回滚写死，模型只负责局部理解 |
| 步骤不固定、需要搜索和判断、结果可检查 | 受约束的 Agent | 限制工具目录、最大循环、完成证据和失败出口 |
| 前半段需要规划，后半段必须确定性执行 | 混合方案 | 让模型提出计划，让代码校验并执行关键动作 |

### 工具调用要当作产品接口设计

工具描述会影响模型是否选中它、传入什么参数和何时停止。每个工具至少要有以下契约：

| 设计项 | 需要写清的内容 |
|--------|----------------|
| 名称与用途 | 用用户能理解的动词命名，明确“能做什么”和“不能做什么” |
| 输入 Schema | 类型、必填项、枚举值、长度限制、格式校验和默认值 |
| 权限范围 | 当前用户、当前租户、可读资源、可写资源和不可访问资源 |
| 副作用 | 只读、可逆写入、不可逆写入；是否会产生费用或对外发送 |
| 幂等性 | 重复调用会不会重复扣款、重复建单或重复发送 |
| 超时与错误 | 超时、鉴权失败、业务拒绝、空结果分别返回什么错误码 |
| 返回证据 | 返回状态、资源 ID、时间戳、来源和可供下一步判断的字段 |

OpenAI 的 Function Calling 文档描述了模型生成结构化工具调用、由应用执行并把结果回传给模型的基本循环；MCP 解决的是 Agent 与外部工具/资源如何连接的问题。两者都不等于业务权限系统，真正的鉴权和参数校验必须在工具服务端再次执行，不能只相信模型的判断。

## 三、状态与记忆：让任务可暂停、可恢复、可解释

不要只把 Agent 当成一段对话。生产产品需要保存**任务状态**，并区分“这次任务的临时上下文”和“跨任务长期保留的记忆”。

### 推荐的最小状态机

```text
created → planning → running_tool → observing
              ↑           │             │
              │           ├─ 可重试 ────┘
              │           ├─ 需确认 → waiting_approval
              │           └─ 达到上限 → blocked
              └────────────┴─ 继续规划

waiting_approval → approved → running_tool
                 └ denied/cancelled → cancelled
observing → succeeded / failed / handed_off
```

状态名要能回答三件事：用户现在是否需要操作、系统是否还会继续消耗资源、运营是否可以恢复任务。暂停状态不能悄悄变成后台继续执行；用户取消后也不能因为队列重试而重新触发副作用动作。

### 短期状态与长期记忆

| 类型 | 适合保存 | PM 要求 |
|------|----------|---------|
| 短期状态 | 当前计划、中间结果、工具返回、待确认动作 | 绑定任务 ID，支持恢复、取消和过期 |
| 长期记忆 | 用户明确授权保存的偏好、稳定配置、历史结论 | 说明用途、来源、有效期、修改和删除方式 |
| 不应保存 | 密钥、完整支付信息、无必要的敏感原文、无法验证的模型猜测 | 默认不保存；需要时只传最小必要字段 |

**建议**：每条记忆都记录来源和时间，不把模型生成的推断自动当成用户事实。让用户能查看、纠正和删除长期记忆；对跨租户、跨用户共享的知识，优先走有权限的知识库/RAG，而不是混进个人记忆。

## 四、人工接管与权限：自主性必须有边界

人工接管不是 Agent 失败后的临时补丁，而是高风险任务的正常路径。可以先按副作用做风险分级：

| 风险级别 | 例子 | 默认策略 |
|----------|------|----------|
| 低 | 只读搜索、草稿生成、内部摘要 | 可自动执行，但记录来源和结果 |
| 中 | 创建草稿工单、修改可撤销配置、批量整理文件 | 先预览变更，允许用户编辑或撤销 |
| 高 | 付款、删除、对外发布、发送敏感信息、修改权限 | 展示目标/范围/后果，用户明确确认；必要时重新认证 |

权限链至少要经过：**当前用户身份 → Agent 身份 → 工具权限 → 资源范围 → 动作级权限 → 风险确认**。模型可以提出动作，但不能自行扩大权限。工具服务端要根据当前用户和租户重新鉴权，并校验资源归属、参数范围和目标地址。

确认弹窗不能只写“是否继续”。应至少展示：将要做什么、对哪个对象做、使用哪些数据、可能造成什么后果、是否可撤销，以及拒绝或修改入口。确认应绑定当前任务和当前版本，过期后不能被旧任务重放。

## 五、失败重试、降级与成本上限

Agent 的失败不是一种错误。建议把错误分为四类，并为每类预先定义动作：

| 错误类型 | 典型表现 | 默认处理 |
|----------|----------|----------|
| 暂时性错误 | 超时、网络抖动、服务限流 | 只对幂等步骤有限重试，带退避和总时限 |
| 参数/Schema 错误 | 缺少字段、格式不合法、工具拒绝参数 | 不盲目重试，修正参数或回到计划节点 |
| 业务错误 | 资源不存在、库存不足、用户无权限 | 告知原因，改走替代路径或转人工 |
| 未知/高风险错误 | 返回异常、结果与预期冲突、疑似越权 | 立即暂停，保留现场，要求人工判断 |

**重试的三个硬条件**：知道错误可能是暂时的；重复执行不会叠加副作用；重试次数和总耗时都受上限控制。对非幂等工具，优先通过幂等键、执行状态查询或人工确认来避免重复动作。

任务预算可以拆成：

```text
任务预算 = 模型调用预算 + 工具调用预算 + 时间预算 + 人工复核预算
```

模型调用预算不仅看 token，还要考虑规划轮数、工具结果被反复塞回上下文的放大效应。达到任一上限就进入 `blocked` 或 `handed_off`，向用户解释“已完成什么、卡在哪里、下一步需要谁处理”，而不是继续静默烧资源。

## 六、审计日志与完成标准

日志要同时服务于三类人：用户需要知道发生了什么；运营需要定位 Badcase；安全和合规需要追责与复盘。建议记录以下事件字段：

- `task_id`、`trace_id`、用户/租户标识、创建和结束时间、当前状态；
- Agent、模型、Prompt/Policy、工具版本；
- 每个计划步骤、工具名、参数摘要、权限判定、确认人和确认时间；
- 工具返回状态、错误码、重试次数、输入/输出 token、延迟和费用；
- 最终完成证据、人工接管原因、用户取消原因和回滚结果。

日志不等于把所有原文都存下来。敏感字段应脱敏或哈希，访问应分级，保留周期应与业务和合规要求对齐。调试日志、用户可见活动记录和安全审计日志可以分层存储，但三者应能通过任务 ID 关联。

一项任务对用户的完成回执，至少应包含：

```text
完成状态：成功 / 部分完成 / 等待确认 / 失败 / 已转人工
已完成：动作、对象、结果证据
未完成：原因、影响范围、是否会继续执行
下一步：用户需要确认、补充信息或联系谁
```

## 七、上线前自查清单

- [ ] 任务卡写清了目标、范围、完成证据和不支持场景。
- [ ] 每个工具都有输入校验、权限范围、副作用、幂等性和错误码。
- [ ] Agent 有明确状态机，用户取消后不会继续执行副作用动作。
- [ ] 短期状态、长期记忆和敏感数据的保存边界已区分。
- [ ] 高风险动作会展示目标、范围和后果，并要求当前用户确认。
- [ ] 重试只覆盖可识别的暂时性错误，且有次数、时间和费用上限。
- [ ] 任务、模型、Prompt、工具、权限、确认和结果证据可以通过日志关联。
- [ ] 任务级成功标准已经进入评测集，并能在灰度期间和线上指标对应起来。
