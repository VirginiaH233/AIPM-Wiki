# 模型选型决策框架:效果、成本、延迟、合规四要素

> 价格截至 2026-07,以官方定价页为准。本文引用的模型单价参考[《AI 产品成本测算入门》](llm-cost-101.md)中的价格对比表。

"该用哪个模型"是 AI PM 最常被问到、也最容易拍脑袋回答的问题。很多团队默认"选最强的模型"或"选最便宜的模型",两种做法都容易踩坑——前者浪费预算,后者伤害体验。本文给出一套可以落地评审的四要素框架:**效果、成本、延迟、合规**,以及配套的选型流程和团队分工建议。

## 一、四要素总览

| 要素 | 核心问题 | 典型冲突 |
|------|----------|----------|
| 效果(Quality) | 模型能不能把这个任务做对、做好? | 效果越好的模型通常越贵、越慢 |
| 成本(Cost) | 按这个方案跑,规模化后账单能不能承受? | 便宜的模型可能需要更复杂的 Prompt/更多轮重试,隐性成本更高 |
| 延迟(Latency) | 用户能不能接受这个响应速度? | 低延迟往往要牺牲模型规模或牺牲效果 |
| 合规(Compliance) | 数据出不出境?内容安不安全?能不能审计? | 最合规的方案(自建/国产/私有化)往往效果或成本不占优 |

选型的本质,不是找到"四项全优"的模型(几乎不存在),而是**明确任务对四要素的优先级排序**,再做取舍。下面逐一展开。

## 二、效果:怎么评估"好不好"

### 评估方法

| 方法 | 适用阶段 | 说明 |
|------|----------|------|
| 公开 Benchmark(如 MMLU、GPQA、行业垂类榜单) | 候选池初筛 | 快,但和你的实际任务可能不对齐,只能做参考不能做决策依据 |
| 自建评估集 + 人工评分 | 选型中期 | 用真实业务场景的 100-300 条样本,让标注/业务人员打分,是最可信的方法 |
| 模型互评(LLM-as-judge) | 大规模评估 | 用强模型给候选模型的输出打分,能规模化但要警惕评委模型本身的偏好偏差 |
| 影子测试/线上 A/B | 上线前最后一步 | 真实流量下对比核心业务指标(转化率、满意度、复购等),而不只是"回答质量分" |

### PM 该问的问题清单

- 这个任务的"好"是怎么定义的?是事实准确、逻辑严密,还是语气得体、格式规范?不同任务对效果的定义完全不同。
- 我们有没有一份能代表真实用户输入分布的测试集?(避免只用"简单干净"的样例测试,上线后被长尾 case 打脸)
- 效果的评估是一次性的,还是要建立持续监控(防止模型升级、Prompt 改动导致效果悄悄下滑)?
- 多大的效果差距才值得多付钱?(比如"贵 3 倍但准确率只高 2 个百分点",大概率不值得)

## 三、成本:延续上一篇的估算方法

成本要素的落地方法已经在[《AI 产品成本测算入门》](llm-cost-101.md)详细展开,这里只列选型时要追问的问题清单:

- 这个任务的输入 token 量级是多少?是否有长文档/长历史对话,导致输入成本远高于输出成本?
- 是否可以用小模型完成大部分请求,只把疑难请求路由给大模型?(分层策略见下一节)
- 这个场景是否是异步/非实时的?能不能用 Batch API 拿到官方 50% 左右的折扣?
- 调用量的增长曲线是怎样的?今天算的账,3 个月后渗透率翻倍还成立吗?

## 四、延迟:用户能接受多慢

| 指标 | 含义 | 产品影响 |
|------|------|----------|
| 首 token 延迟(TTFT) | 用户发出请求到看到第一个字返回的时间 | 直接决定"感觉快不快",流式输出可以大幅改善这个体感 |
| 总生成时间 | 完整回答生成完的总耗时 | 输出 token 越多耗时越长,长回答场景要考虑限制输出长度 |
| 并发/排队延迟 | 高峰期请求排队等待的时间 | 容易被忽略,压测时只测单请求延迟,忽略了并发下的真实体验 |

### PM 该问的问题清单

- 这个场景是同步等待(用户盯着屏幕等),还是异步通知(比如生成报告后推送)?同步场景对延迟敏感得多。
- 能不能用流式输出改善体感?(哪怕总耗时一样,"边生成边看到"比"转圈等待"体验好很多)
- 高峰期的并发量级是多少?选型时是否测过高并发下的延迟劣化,而不只是单请求延迟?
- 是否可以用"快速模型先给初步结果,慢速模型异步优化"的分级体验来兼顾速度和效果?

## 五、合规:容易被低估的一环

合规不是"选完模型再补的手续",而是应该在选型早期就参与筛选候选池的硬约束。

### PM 该问的问题清单

- 数据能不能出境?哪些字段是敏感信息(身份证、病历、金融账户等),是否有强制的数据本地化/国产化要求?
- 模型供应商是否承诺不用客户数据训练?合同条款是否明确?
- 是否需要满足特定行业监管(金融、医疗、教育)对 AI 生成内容的审计、留痕、可解释性要求?
- 内容安全:是否有内置的内容审核能力,还是需要自建一层审核?
- 版权风险:生成内容是否可能涉及版权纠纷(尤其是图片、代码类场景)?

**建议**:把合规当作"一票否决项"先过滤候选池,再在剩下的候选中比较效果、成本、延迟——顺序反了容易做无用功(选型选到一半才发现某模型不能用于你所在的行业/地区)。

## 六、大小模型分层策略

实践中很少有产品只用一个模型跑所有请求,更常见的做法是分层:

| 层级 | 典型模型定位 | 承接的请求 | 占比参考 |
|------|--------------|------------|----------|
| 轻量层 | Haiku 级 / mini・nano 级 / Flash-Lite 级 | 意图识别、简单分类、格式化提取 | 60-70% |
| 主力层 | Sonnet 级 / 主力级 / Flash 级 | 常规问答、大部分业务场景 | 20-30% |
| 旗舰层 | Opus 级 / 旗舰级 / Pro 级 | 复杂推理、长文档理解、高风险决策 | 5-10% |

分层的关键不是"哪个模型好",而是"用一个足够便宜/足够快的分类器,把请求准确路由到合适的层级"。路由误判是这套策略最大的风险——把复杂问题误判成简单问题、发给轻量模型,会直接反映在用户体验上。具体的路由实现和节省幅度测算,见[《降本手段盘点》](cost-optimization.md#四小模型路由分级服务)。

## 七、自建 vs API:什么规模才值得考虑私有化部署

这是几乎每个团队都会讨论、但常常没有结论的问题。给出一个粗略的决策框架:

| 决策维度 | 倾向 API 直连 | 倾向自建/私有化部署 |
|----------|----------------|----------------------|
| 调用规模 | 日调用量在百万级 token 以内,或业务尚在验证期 | 日调用量达到十亿级 token 以上且长期稳定,GPU 成本摊薄后低于 API 账单 |
| 团队能力 | 没有专职的模型部署/推理优化团队 | 有算法工程团队能做推理优化(量化、批处理、vLLM 等) |
| 合规要求 | 数据可以出境,或供应商已满足合规要求 | 数据绝对不能出企业内网/必须国产化替代 |
| 迭代速度要求 | 需要跟着最新最强模型快速迭代 | 任务边界清晰、模型能力已经"够用",不需要追新 |
| 场景定制化程度 | 通用能力即可满足 | 需要针对垂类场景深度微调,通用 API 效果始终不达标 |

**一个直观的判断方法**:先用上一篇的估算模板算出"如果一直用 API,月成本是多少";再找算法/基础设施同事估一个"自建需要多少张 GPU + 多少运维人力";两者做 12-18 个月的总拥有成本(TCO)对比,而不是只比"单价"。很多团队自建后发现,GPU 利用率不足、运维投入被低估,实际成本并不比 API 便宜——所以自建决策一定要拉上算法/基础设施团队一起测算,PM 不该单方面拍板。

## 八、选型评审的落地流程

一套可以直接搬进团队评审会的流程:

```
1. 需求定义
   明确任务类型、效果底线、延迟要求、合规硬约束(一票否决项先过滤)

2. 候选池筛选
   基于公开 Benchmark + 供应商资质,筛出 3-5 个候选模型/层级组合

3. 评估集设计
   用真实业务分布抽样 100-300 条,覆盖典型 case 和已知的长尾 case

4. 离线评测
   跑候选模型,人工/LLM-judge 双重打分,同时记录延迟和 token 消耗

5. 成本测算
   用llm-cost-101.md 的模板,按候选模型分别测算规模化后的月成本

6. 影子测试/小流量 A/B
   选出 Top 1-2 候选,在真实流量上小比例验证核心业务指标

7. 上线与监控
   设定效果/成本/延迟的监控阈值,定期(建议每季度)复评——模型和价格都在持续变化
```

## 九、和算法工程师的分工边界

选型不是 PM 一个人的工作,明确分工能减少来回拉扯:

| 事项 | PM 该做的 | 该交给算法工程师的 |
|------|-----------|---------------------|
| 定义"好"的标准 | 主导:业务目标、用户体验标准、效果底线 | 参与:补充技术可行性意见 |
| 评估集设计 | 主导:样本来源、覆盖场景、优先级 | 协作:统计方法、评测工具搭建 |
| 模型/参数调优 | 不该管:Prompt 底层细节、模型超参数、推理优化 | 主导 |
| 成本估算 | 主导:业务侧参数假设(调用量、渗透率) | 协作:单价、推理优化后的实际成本 |
| 自建可行性 | 参与:业务规模判断、ROI 测算 | 主导:技术选型、部署方案、运维评估 |
| 上线监控指标 | 主导:业务指标(满意度、转化) | 协作:技术指标(延迟、错误率、漂移检测) |

**一句话原则**:PM 该对"要什么效果、能接受什么代价"有清晰判断,不该替算法工程师决定"怎么实现"。把决策权放在正确的人身上,选型才能又快又准。
