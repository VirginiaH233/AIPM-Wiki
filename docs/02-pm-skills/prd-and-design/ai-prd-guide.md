# AI 产品 PRD 怎么写:与传统 PRD 的核心差异

## 一句话核心差异

传统 PRD 回答的问题是"做什么、什么时候上线、交互长什么样";AI 产品的 PRD 除了这些,还必须回答一个传统 PRD 从不需要回答的问题——**"效果好到什么程度才算做完"**。这是因为传统功能是确定性的(按钮点了就跳转,规则命中就执行),而 AI 功能是概率性的(同一个问题,模型今天答对,明天可能答错)。这个本质差异,决定了 AI PRD 必须新增几个传统 PRD 里没有的章节。

关于 AI PM 和传统 PM 差异的整体认知,可先看 [AI 产品经理和传统产品经理最大的区别是什么?](../../04-interview/behavioral/ai-pm-vs-traditional-pm.md);本文聚焦到**文档层面**,回答"这些差异具体要落到 PRD 的哪些章节、怎么写"。

## 传统 PRD vs AI PRD:多出来的章节

| 传统 PRD 章节 | AI PRD 是否需要 | AI PRD 额外新增 |
|--------------|-----------------|-----------------|
| 需求背景与目标 | 需要,不变 | — |
| 用户故事 / 交互流程 | 需要,但要加"AI 判断失败时怎么办"的分支 | 兜底交互流程 |
| 功能规格(字段、状态、边界条件) | 需要,但边界条件从"参数校验"变成"能力边界" | 能力边界与不承诺清单 |
| 验收标准 | 传统 PRD 是"功能跑通即验收";AI PRD 不能这样验收 | **效果定义章节**(核心新增) |
| 上线计划 | 需要 | 数据需求与回流设计、成本预算章节 |
| 埋点与数据指标 | 需要,但要新增模型层指标 | 评测集与及格线 |

可以看到,AI PRD 不是把传统 PRD 推倒重来,而是在原有骨架上,把"验收标准"这一节从一句话("功能正常可用")展开成了四个独立章节。下面逐一拆解。

## 一、效果定义章节:怎么写

这是 AI PRD 与传统 PRD 最大的分野。传统功能的验收是二元的(能用/不能用),AI 功能的验收是一个**分布**——你要先定义"够好"是什么样子,再证明模型/系统达到了这个水位。

一个完整的效果定义章节,至少要包含三块:

### 1. 目标指标(要分层,不能只写一个"准确率")

| 指标层级 | 举例 | 谁来看 |
|---------|------|--------|
| 模型层指标 | 准确率、召回率、BLEU/ROUGE、幻觉率 | 算法团队日常调优 |
| 产品层指标 | 任务完成率、人工介入率、用户采纳率(是否直接使用 AI 输出而不修改) | PM 判断功能是否达标 |
| 业务层指标 | 留存、转化、人效节省、投诉率 | 老板判断这个功能值不值得做 |

三层指标要写清楚**因果链条**假设,例如:"模型准确率从 85% 提到 92% → 人工复核率从 40% 下降到 15% → 客服人效提升 20%"。这条链条本身就是需要在效果定义章节里明确写出、后续验证的假设,而不是想当然。

### 2. 评测集(测试集从哪来、怎么维护)

- **来源**:历史真实数据(优先)、人工构造的边界 case、竞品/业界公开 benchmark(仅作参考,不能替代业务数据)
- **规模与代表性**:至少覆盖高频场景 + 长尾困难场景 + 已知的历史 bad case;避免"测试集全是简单题"导致的虚假高分
- **标注标准**:谁来定"这个回答算对";主观任务(如文案生成)要写清打分维度和评分细则,而不是"看着还行"
- **更新机制**:评测集不是一次性交付物,业务变化、新 bad case 出现后要迭代;写清楚"谁负责评测集的持续维护"

评测集的具体建设方法论,可参考 [model-evaluation/](../model-evaluation/README.md) 板块。

### 3. 及格线(Pass Bar):上线前必须明确的数字

及格线要写成可验证的具体数字,而不是"效果要好"这种无法验收的话。例如:

- 核心场景准确率 ≥ 90%,且 P0 高风险场景(如涉及金额、合规)准确率 ≥ 99%
- 幻觉率(编造事实的比例)≤ 2%
- 人工介入率(转人工/拒答比例)首月 ≤ 30%,并有季度下降计划
- P95 响应延迟 ≤ 3 秒

**及格线要区分"上线线"和"目标线"**:上线线是不达标就不能上线的红线,目标线是长期优化方向。两条线混为一谈,是很多 AI 项目"效果不够也硬上"的根源——这也是 [AI 产品如何判断 PMF、如何冷启动、兜底策略怎么设计?](../../04-interview/product-design/ai-product-pmf-coldstart-fallback.md) 里提到的典型踩坑场景。

## 二、能力边界与不承诺清单

传统 PRD 的"功能边界"写的是参数范围(如"最多上传 10 张图");AI PRD 的"能力边界"写的是**这个功能不擅长、甚至不该用来做什么**。这一节最容易被忽略,却是防止用户预期跑偏、防止业务方"既要又要"的关键武器。

建议按下面的结构写:

| 分类 | 示例 |
|------|------|
| 明确支持的场景 | "支持中文电商退换货政策问答" |
| 明确不支持的场景 | "不支持法律纠纷判定,涉及此类问题一律转人工" |
| 已知的失败模式 | "对多轮嵌套条件(如'如果A且不是B,除非C')准确率会显著下降" |
| 不承诺的效果 | "不保证每次回答完全一致(温度参数导致的随机性)" |
| 风险场景的强制阻断 | "涉及金额修改、账户注销,AI 只能建议,不能自动执行" |

这一节本质上是在做"提前透露局限性",避免上线后被用户投诉"说好的智能客服怎么这都不会"。这个思路可以直接类比 Anthropic、OpenAI 发布模型时的 **System Card**(系统卡)——下文详细展开。

## 三、数据需求与回流设计

AI 功能上线不是终点,而是"数据飞轮"的起点。这一节要写清楚三件事:

1. **冷启动数据从哪来**:历史日志、人工标注、专家写的种子数据、第三方数据采购——分别写明来源、数量级、质量把控方式。
2. **线上数据怎么回流**:用户的每一次点赞/点踩/编辑/转人工,都是潜在的训练/评测信号,要在 PRD 里明确"这些行为数据流向哪个系统、多久处理一次、谁负责看 bad case"。
3. **数据合规红线**:哪些用户数据可以用于模型迭代,是否需要脱敏,是否需要用户授权——这条不写清楚,后期极易埋雷。

具体的数据标注规范和冷启动方法论,见 [data-annotation/](../data-annotation/README.md) 板块。

## 四、成本预算章节

传统 SaaS 功能上线后,多一个用户的边际成本趋近于零;AI 功能不同,**每一次用户请求都在真金白银地花钱**(token 消耗)。这一节至少要写清楚:

| 成本项 | 说明 |
|--------|------|
| 单次调用成本 | 按预估的输入/输出 token 量 × 模型单价估算 |
| 并发/规模化成本 | DAU × 人均调用次数 × 单次成本,给出月度总成本估算 |
| 成本上限与告警 | 超过预算阈值时是否自动降级到更便宜的模型或规则兜底 |
| 降本路线图 | 缓存高频问题、小模型分流简单任务、按需微调替代长 Prompt 等 |

成本测算的详细方法,可参考 [cost-and-tech/](../cost-and-tech/README.md) 板块,以及面试题 [某功能接入大模型后成本涨了 10 倍,如何降本?](../../04-interview/case-analysis/reduce-llm-cost-10x.md) 中的成本拆解框架。

## 类比:向 Model Card / System Card 学"效果怎么披露"

Anthropic 和 OpenAI 每次发布新模型,都会同步发布一份 **System Card**(系统卡,早期也叫 Model Card)。以 2026 年 Anthropic 发布的 Claude Sonnet 5 System Card、Claude Opus 4.6/4.8 System Card,以及 OpenAI 的 GPT-5 系列 System Card 为例,它们的公开结构通常包含:能力评测结果(在哪些 benchmark 和"生产场景真实困难案例"上的表现)、安全评估(红队测试、滥用风险测试)、已知局限性、以及负责任部署决策(在什么条件下才允许开放什么能力)。

这套披露逻辑,和 AI PRD 里"效果定义 + 能力边界"两节想解决的问题几乎一模一样:**不是等用户发现模型不会什么,而是主动、具体地讲清楚模型能做什么、不能做什么、在什么水位上是可信的**。区别在于系统卡面向的是外部世界和监管,AI PRD 面向的是内部团队和验收流程,但"用具体数字和具体场景说话,而不是用形容词"这条原则是相通的。写效果定义章节卡壳时,不妨反问自己:如果要把这个功能的效果写成一份对外的"系统卡",你有没有底气写出具体的评测结果和边界说明?写不出来,往往说明效果定义还不够扎实。

## AI PRD 章节模板(可直接套用)

```markdown
# [功能名称] PRD

## 1. 背景与目标
- 要解决的业务问题
- 为什么用 AI 而不是规则/人工(参考:这个问题是否适合用 AI 解决)

## 2. 用户故事与交互流程
- 正常路径(AI 回答符合预期)
- 异常路径(AI 不确定/答错/超出能力边界时的兜底流程)

## 3. 效果定义(AI PRD 核心新增)
- 3.1 目标指标(模型层 / 产品层 / 业务层,及三者的因果假设)
- 3.2 评测集(来源、规模、标注标准、更新机制)
- 3.3 及格线(上线红线 vs 长期目标线,给出具体数字)

## 4. 能力边界与不承诺清单
- 明确支持的场景
- 明确不支持的场景
- 已知失败模式
- 不承诺的效果
- 高风险场景的强制阻断规则

## 5. 数据需求与回流设计
- 冷启动数据来源
- 线上数据回流机制(埋点、bad case 收集、标注分发)
- 数据合规红线

## 6. 成本预算
- 单次调用成本估算
- 规模化后的月度成本
- 成本告警阈值与降级策略

## 7. 兜底与风险
- 置信度分级与降级链路(详见交互设计文档)
- 人工介入触发条件

## 8. 上线计划与灰度策略
- 灰度范围、观察周期、回滚条件

## 9. 后续迭代计划
- 数据飞轮:下一轮优化的数据来源和验证方式
```
