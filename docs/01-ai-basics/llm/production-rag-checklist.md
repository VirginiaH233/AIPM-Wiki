# 工业级 RAG 清单:混合检索、重排、评测与知识治理

"接个向量库,跑通一个 Demo"和"这套检索系统能稳定支撑生产流量"之间,中间隔着一整条容易被低估的工程与治理链路。Demo 阶段大多只验证了"问题问得标准、知识库很干净"这一种情况;生产环境要面对切片切坏了、文档过期了、权限混了、评测样本不够代表真实分布等一堆"非理想情况"。本文把这条链路拆成可核对的清单,接着[《RAG 没死:死的是 Naive 固定流水线》](rag-evolution-naive-to-agentic.md)往细节走。

## 从 Demo 到生产的缺口清单

| 环节 | Demo 阶段常见做法 | 生产阶段要多做的事 |
|------|-------------------|---------------------|
| 切片(Chunking) | 固定字数硬切 | 按文档结构(标题/段落/表格)切,避免语义单元被截断 |
| 元数据 | 不带或只带文件名 | 补充来源、版本、时间、权限标签,支撑过滤与溯源 |
| 权限 | 全库统一可见 | 检索前按用户/租户过滤,而非生成后再遮蔽 |
| 更新 | 一次性导入,不再变 | 明确的增量更新、失效剔除机制,避免"新文档查不到、旧文档删不掉" |
| 评测 | 抽几个问题人工看看 | 有覆盖高频+长尾+边界 case 的评测集,能持续跑回归 |
| 引用 | 不展示来源 | 附带可点击的原文出处,是用户信任和排查问题的基础 |
| 降级 | 检索不到就让模型自由发挥 | 明确"查不到就说不知道"还是"转人工"的兜底路径 |

这张清单里最容易被跳过的往往不是技术难度最高的一项,而是"元数据"和"更新机制"——它们在 Demo 里显得无关紧要,却是生产环境里权限、时效性问题的根源。

## 混合检索:向量 + BM25 是及格线,不是加分项

单独的向量语义检索有一个稳定的弱点:对专有名词、型号、工单号这类需要"字面精确命中"的查询不敏感。生产级检索的及格线,是**向量语义检索 + BM25 关键词检索的混合召回**,而不是只优化一条向量索引的召回率。

Anthropic 在《Introducing Contextual Retrieval》中给出了一组可引用的方法论数据:在检索前为每个文本块补充"上下文说明"(Contextual Embeddings),再叠加同样带上下文的 BM25(Contextual BM25)进行混合检索,能把 Top-20 检索的失败率降低约 **49%**;在此基础上再加一层重排序,失败率能再降低到约 **67%**。这组数字来自 2024-09 发布的方法论文,不是随模型迭代实时更新的动态指标,复现效果取决于具体知识库和查询分布,但它验证的方向是明确的:**混合检索 + 重排,在多数场景下比单独打磨一种检索方式的投入产出比更高**。完整的路径对照见[《RAG 系统有哪几种检索路径?》](../../04-interview/basics/rag-multi-retrieval-paths.md)。

## Rerank 与 Top-K 裁剪:精度和成本的杠杆

多路召回解决的是"覆盖",重排序(Rerank)解决的是"精度"——先用低成本的方式召回足够多的候选,再用更贵但更准的模型把真正相关的候选排到前面,最后只把 Top-K 喂给生成模型。这里有两笔账要提前算清楚:

- **Top-K 太大**:生成阶段的输入变长,成本和延迟都上升,还可能引入"中间遗忘"风险,细节见[《长上下文 vs RAG》](long-context-vs-rag.md)。
- **Top-K 太小**:召回的证据不够,复杂问题答不全,却更容易被误判成"生成模型能力不够"而不是"证据给少了"。

Rerank 模型本身也是一次额外调用,要计入端到端延迟和成本预算,不是"免费加上去更保险"的选项。一个常见的落地策略是:简单查询走轻量重排或直接跳过,只有召回候选数量大、歧义高的查询才启用完整的重排链路。

## 评测:检索召回与答案质量要分开看

"RAG 准不准"从来不是一个单一指标,而是要按环节拆开评测:检索环节看有没有把相关材料找回来,生成环节看模型有没有基于给定材料答好。把两者混在一起评测,排查问题时会经常出现"明明检索到了对的材料,却把锅甩给生成模型"或者反过来的误判。具体的分环节指标和评测集构建方法,见面试题[《如何评估 RAG 知识库的准确率?》](../../04-interview/basics/rag-kb-accuracy-evaluation.md)。

生产阶段还需要一件 Demo 阶段基本不做的事:维护一个**持续增长的坏例集(Badcase Set)**。上线后的真实用户问题、被用户反馈"答非所问"的案例,都应该定期回流进评测集,而不是只用上线前一次性构建的样本反复跑。评测集构建的完整流程可参考[《从零建设评测集》](../../02-pm-skills/model-evaluation/build-your-eval-set.md)。

## 知识治理:谁维护、什么时候过期、权限怎么隔离

检索链路调得再好,知识库本身治理跟不上,答案照样会错。上线前至少要拍板三件事:

1. **谁维护文档**:每一类知识库文档要有明确的责任人,而不是"技术团队负责导入,内容对不对没人管"。
2. **过期策略**:文档失效后是自动下线、打标"已过期仅供参考",还是需要人工确认替换——没有策略的默认结果通常是"旧文档一直混在检索结果里"。
3. **权限与租户隔离**:多租户场景下,检索必须在"进入 Prompt 之前"就按用户身份过滤掉无权限查看的内容,不能指望模型看到了敏感内容后"自觉不说"。

## 什么时候该往上升级

混合检索 + 重排把及格线做扎实之后,再考虑是否需要升级到更复杂的架构,而不是反过来:

- **知识库小、几乎不更新**:可以评估是否直接全量塞进长上下文,权衡见[《长上下文 vs RAG》](long-context-vs-rag.md)。
- **任务出现多步骤、多分支判断**(有时查一次够,有时要查两次、跨文档综合):该升级到 Agentic 检索,让模型自己决定检索策略,而不是死磕更精细的固定流水线,参考[《RAG 没死:死的是 Naive 固定流水线》](rag-evolution-naive-to-agentic.md)。
- **问题的答案在表格/指标里,不在文档片段里**:该走结构化检索 / NL2SQL,而不是把表格数据硬切成文本块塞进向量库,参考[《NL2SQL:自然语言查库,为什么学术高分上不了生产》](nl2sql-for-ai-pm.md)。

## GraphRAG:可选的增强,不是必经的升级

GraphRAG(用大模型从文档中抽取实体关系、构建知识图谱再检索)常被包装成"RAG 的下一代标准形态",但更准确的定位是:**它解决的是一类特定问题——"全局性、跨文档综合"的宏观问题(比如"这批文档整体在讲什么主题"),而不是所有 RAG 场景的通用升级**。Microsoft Research 在官方博客中明确指出,GraphRAG 的收益要和图索引构建的前期成本一起权衡,更适合"需要理解数据全局结构、且值得为此支付索引成本"的场景。国内评测讨论也已经指出,GraphRAG 在具体任务上的表现各有优劣,并非无条件优于混合检索。对大多数"针对具体问题找具体证据"的问答场景,先把混合检索和重排做扎实,往往比直接上图谱更划算。

## 给 AI PM 的清单

1. 切片是否按文档结构切,而不是固定字数硬切?
2. 是否已经是向量 + BM25 混合检索,而不是单一向量检索?
3. 是否有独立的重排环节,Top-K 大小是否经过成本/效果权衡?
4. 检索召回率和答案质量是否分开评测,是否有持续回流的坏例集?
5. 文档是否带权限/时间等元数据,权限过滤是否发生在检索阶段而非生成之后?
6. 知识库是否有明确的维护责任人和过期策略?
7. 检索不到时的降级策略是否明确(拒答 / 转人工 / 澄清追问)?
8. 是否只在真正需要时才升级到 Agentic 检索、NL2SQL 或 GraphRAG,而不是为了追新引入额外复杂度?
